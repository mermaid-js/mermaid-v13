# D652: The PR structural audit fails on what the nightly fallow run fails on, except CRAP and new duplication; a red nightly alerts; amends D640

The nightly fallow run (`fallow-nightly.yml`) was red from its first night after the baselines were saved on 2026-11-12, and every night after (#911). The PR audit (`fallow audit -c .fallowrc.pr.json --base HEAD^1`, gate `new-only`) only warned on findings that the nightly fails on: `private-type-leaks` and `duplicate-exports` were `warn` in `.fallowrc.json`, and the nightly passes `--fail-on-issues`, under which a `warn` rule fails the run. New duplication also only warned on a PR (the `ci.yml` comment said it failed), and the nightly gates duplication against its baseline. Each merge with such a warning turned the nightly red for good. The audit also looks only at changed files, so a finding that a config change causes (a new boundary zone) or that lies in an unchanged file reaches only the nightly. And 751 of the 1,005 entries in `.fallow-baseline/dupes.json` matched nothing.

1. **The findings are fixed and the baselines saved again.** The 13 private type leaks, the 3 duplicate exports and the boundary violation (`language-service-monaco`'s adapters spec imported the language server) are fixed, not suppressed. The dead-code, dupes and health baselines are pruned and saved at the merged tree. The health baseline comes from a run with the full unit suite's coverage, as the nightly runs. The nightly command then exits 0.
2. **The PR audit fails on the dead-code findings the nightly fails on.** `.fallowrc.json` sets every dead-code rule that can fire here to `error`: `private-type-leaks`, `duplicate-exports`, and the rules whose default is `warn` (`unused-dev-dependencies`, `unused-optional-dependencies`, `unused-namespace-members`, `type-only-dependencies`, `test-only-dependencies`, `re-export-cycle`, `package-cycle`, `stale-suppressions`, `unused-catalog-entries`, `empty-catalog-groups`, `unused-dependency-overrides`). The nightly fails on these already, so it does not change. Two kinds still only warn on a PR:
   - CRAP, as D640 decided: the audit has no coverage, so the score is an estimate. Exact CRAP gates in the nightly.
   - New duplication. fallow 3.41's audit has no setting that fails on an introduced clone group: `--fail-on-issues` is ignored by `fallow audit`, and `duplicates.threshold` is a percentage, not a count of new groups. fallow 3.44.0 adds the rule `introduced-clone-group`; setting it to `error` would close this gap, and is left for an upgrade of fallow.
3. **A deliberate clone is accepted in its own PR.** When a change keeps a clone on purpose, the PR saves the dupes baseline again (`pnpm exec fallow dupes --save-baseline .fallow-baseline/dupes.json`) and commits it, and the PR body says why the copy stays. A PR that changes `.fallowrc.json` (rules, zones, the duplication scope) saves the baselines it affects too, because it changes what they mean.
4. **A red nightly alerts.** When the fallow step fails on `mermaid-v13` (on the schedule or by hand), one open issue labelled `nightly-fallow` gets a comment with the run link and fallow's report; when none is open, the workflow opens one. A green run comments on the open issue and closes it. A Slack message (`chat.postMessage`, the bot token in the secret `SLACK_BOT_TOKEN`, the mermaid-ops `comp-status` bot; the channel in the repository variable `FALLOW_SLACK_CHANNEL_ID`) names the failed gates with their counts and links the issue and the run. Without the secret or the variable, the Slack step is skipped with a notice. The alert jobs run no repository code, and only the Slack job sees the token.

This amends D640's split. D640 had the PR audit fail on everything except CRAP; in practice it also let through the warn-level dead-code rules and new duplication. Now the PR audit fails on every dead-code, cycle, boundary and cyclomatic or cognitive finding that the change introduces. The nightly gates exact CRAP, new duplication until fallow can gate it on a PR, and the effects across the tree that a change-scoped audit cannot see.

(Ashish, 2026-11-19, #911.)

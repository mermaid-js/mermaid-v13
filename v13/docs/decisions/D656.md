# D656: Diagram variables follow the overrides v12's follow, and the named classic themes pin the background and line values v12 pins; extends D570

Until 13.0 (D658), v12 decides how each diagram variable responds to an override of a base colour, one variable at a time. In `default`, `forest`, `neutral` and `dark` that cuts both ways:

- Where v12 recomputes a variable from a base colour, v13 does too, even where D570 pinned the shared variable the diagram read before. So a `primaryColor` override recolours journey's sections under `default`, as in v12.
- Where v12 keeps a variable at its constructor value, v13 does too. A diagram table reads a shared variable that the four themes pin to v12's value; where none exists, the theme specs pin one, in `values`, as D570 pinned `mainBkg`. This covers `background` (the xychart and wardley backgrounds, state's composite fill) and `lineColor` (requirement's relations, event modelling, wardley, and architecture under `dark`) as well as the fills and text inks.

This replaces D388: under `default`, xychart's derived colours no longer follow an author's `primaryTextColor` and `background`, as in v12.

No diagram table names a theme (D331). `base` is unchanged: it derives from its base colours, as v12's does. Where v13 keeps a different response on purpose, the type's override spec lists it under a decision with a MIGRATION row (D654).

Rejected: letting lines follow an author's `lineColor` in every theme and recording it, as D351 did for radar and D575 for arrowheads. One variable at a time keeps a single rule for the spec; D351 and D575 stand.

(Knut, 2026-11-19, spec #1035.)

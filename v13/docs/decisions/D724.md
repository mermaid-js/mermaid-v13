# D724: A wrapped message between neighbouring participants wraps inside their lifelines

A wrapped message between two participants with no shown participant between them wraps at `span − 2·wrapPadding`, where `span` is the length of its line. Its label stays `wrapPadding` clear of both lifelines, with `messageAlign` set to `center`, `left` or `right`. Cells already wrapped every message this way. A self message and a message across several columns keep v12's rule, `max(span + 2·wrapPadding, width)`. This is a deliberate divergence from v12.

## What v12 does

v12's `buildMessageModel` wraps a message at `max(span + 2·wrapPadding, sequence.width)`, and v13 used the same formula. Either way a full line is up to `2·wrapPadding` wider than the line under it, so it runs past both lifelines. The gap between two participants is sized the same way in both versions: v12's `getMaxMessageWidthPerActor` wraps at `width − 2·wrapPadding`, then adds `2·wrapPadding` and `actorMargin`. Both examples in #1239 get lifelines 200 px apart in both versions.

Measured in Chromium with the conformance oracle's mermaid 12.2.0 (spec #1337, T4):

- `Bob-x John:wrap: John! Are you still debating about how you're doing? How long does it take??` wraps at 212 px in both versions. v12's label crosses Bob's lifeline by 8.2 px and John's by 2.2 px. v13's crossed by 7.9 and 1.9.
- In `should-handle-line-breaks-and-wrap-annotations.mmd`, the same message crosses by 18.4 and 12.4 px in v12, and by 8.1 and 2.1 in v13 before this change.
- With `messageAlign: left` and `wrap: true`, `A->>B: a message that is long enough to see the alignment and wrapping happen` crosses B's lifeline by 46.7 px in v12, and by 17.3 in v13 before this change.

The v12.3.0 screenshot in #1239 shows the same lines crossing both lifelines. #1239 assumed that v12 keeps wrapped text between the lifelines, and the measurements show it does not.

v12 overruns further than v13 because it measures in the wrong font. `bounds.init()` copies the top-level `fontFamily`, `"trebuchet ms", verdana, arial, sans-serif;` with its trailing `;`, into `messageFontFamily`. Chromium drops that inline style as invalid, so v12 measures each line in the page default font, Times, and draws it in the diagram font, about 8–13 % wider than it measured. v13 measures in the font it draws in and does not copy that bug.

## The choice

Knut chose to keep wrapped text between the lifelines, as an improvement on v12 (option b of spec #1337, 2026-11-26). The other option was to close #1239 as matching v12. In px, `geometry.ts` now applies the cells rule to messages between neighbouring participants. A narrower wrap gives a long label more lines, so the rows grow. With the default config that is 16 px for the `messageAlign: left` example and for the fixture, nothing for the minimal `Bob-x John` example.

The gap sizing in `columns.ts` does not change. It sizes the gap from the label wrapped at `width − 2·wrapPadding`. With the default `actorMargin`, that leaves `span − 2·wrapPadding` at least 42 px wider than that label, so a label wrapped inside the span takes no more lines than the gap sizing assumed. A word wider than the span is broken, so the label never reaches a lifeline. With a small `actorMargin`, or with activation bars that narrow the span, the label only gets more lines.

The layout invariants check that the label of a wrapped message between neighbouring participants stays between their lifelines in px (`wrappedInside` in `layout/invariants.ts`). They skip a message whose line itself leaves the lifelines, which happens when activation bars wider than the gap cover the other lifeline.

The conformance divergence list (`packages/conformance/divergences/`) holds parser divergences only (`accept`, `reject`, `model`), so this layout divergence is recorded here and in the sequence migration fragment.

(Knut, 2026-11-26, spec #1337, #1239.)

# D718: Named-side routes under layered get lanes

Under `layered`, an edge whose side is named (`LayoutEdge.sides`, D503) is drawn again after layout, from its sides. Before, only an edge whose named side moved an end was drawn again; each saw only the nodes as walls, every end on one side started at that side's middle, and the route went through layered's label point. In #1212 that drew two lines along one run, a line that looped round another, and a long diagonal through an invisible junction. Now:

- **Every route drawn again is a wall for the ones after it.** A later route may cross it, but it may not run along it: a leg that runs the same way within half a port pitch (8 px) of an earlier one costs what running through a node costs. Two routes drawn again share no run longer than a corner (12 px).
- **Every edge that names a side is drawn again,** not only one whose end moves. Where layered's sides were already the named ones, layered's route was its own curve or diagonal, which the routes drawn again could neither avoid nor be told apart from. In #1212 the line from `j1` to `j2` was a long diagonal. One exception: where the named sides are the ones layered took, and the route drawn again would run through a node that layered's route went round (see the limit below), layered's route stays, label and all. A self-loop whose sides are the ones layered's loop took keeps that loop, as does an edge between a node and its own group.
- **The named ends on one side of a node are spread along it,** as layered spreads its own: `portPitch` apart, less on a short side, a `corner` clear of each end of the side, centred where one end alone would go (the middle, or `anchorY` down a left or right side). On a side too short for its two corners, the ends move into the corners' room, as far from each other as from either end of the side, so that no two meet. They are ordered by where each edge's far end lies, read before any side is spread, so that they do not cross and the order the edges come in does not move them. Of two ends whose edges turn the same way, the one further from the turn gets the longer stub, so that their runs out are a pitch apart.
- **The route no longer goes through layered's label point.** That point lies where layered's own route ran, and reaching it from a side layered did not take turned routes back on themselves. Once every route is drawn, each label goes beside its route, half a port pitch off it, on a leg between the stubs, at the place nearest layered's label point where it covers no node, no route, no label placed before it and no group's title, and lies across no group's border. Where every such place covers something, it takes the one that covers fewest, still beside its route. The drawing grows to hold it. The end labels (D102) are then placed again beside the routes as drawn, clear of the labels.
- **A leg that runs within half a corner of a node costs a little more,** so that of two routes that are otherwise as good, the one that keeps clear of the nodes wins. In #1212 the line to `j2` no longer runs 4 px above Right.

Placement stays layered's: ranks, order and boxes do not move, and D560 holds, with its one `ARCHITECTURE_PLACEMENT_IGNORED` warning. A graph in which no edge names a side is laid out exactly as before. This amends no decision. It refines how D503's hints are drawn.

**Packaging (D557).** The redraw is a core subpath of its own, `@mermaid-js/core/layout/sides`, which core's index does not re-export: `honourSides(graph, model)`, which takes `layered`'s model of a graph and returns it with the named sides drawn. `layered` itself reads no side. Architecture, the only diagram whose edges name sides, calls it on the model `ctx.layout` returns when its engine is `layered` or `dagre`, so it loads with the architecture chunk, and `renderSync` needs nothing preloaded. The graph stays plain data (DESIGN §6.1): no function rides on it. Flowchart names no side, so its closure (R-PERF-1) no longer carries the code: core and loaded are each about 1.1 KB gz smaller than at `mermaid-v13`, and the architecture chunk is about 2.3 KB gz larger. `OUTWARD` moves to `layered/end-markers.ts`, which layered already loads. Under `availableWidth`, `layered` chooses between its loose and tight layouts by their widths before the redraw, which can grow the drawing by a stub's reach into the margin.

Limit (#525 GAPS, T0b): between its two stubs a route has at most two corners. Where a route needs more to go round a node, it still runs through it, as before, unless its sides are the ones layered took and layered's route went round that node: then layered's route stays. One example that still runs through is a line from a hub's right side to a service in the rank below another service.

Confirmed by Knut, 2026-11-27 (taken overnight, spec #1335):

- **Every named-side edge is drawn again, not only those whose end moves,** except where the sides are layered's own and the redraw would run through a node that layered's route went round (review of #1366). This removes the diagonal in #1212 (its fixture keeps no diagonal), and every architecture line under `layered` that the redraw can draw clear is square; one it cannot keeps layered's curve or diagonal. The alternative is to draw again only the edges whose end moves, as before; the diagonal stays. Switching back means restoring the old `moved` gate in `honourSides` and the two D503 tests that pinned it ("changes nothing where the sides named are the ones layered took"). It costs or saves only a few bytes.
- **The label moves beside its route instead of the route going through it** (the spec's open point). The alternative is to keep the waypoint: labelled routes then double back, as in #1212's labelled variant. That saves about 270 B gz of the change's 632 B, but leaves loop-backs on every labelled edge whose side layered did not take.
- **Layered reads no side; the diagram that names sides calls `honourSides` on layered's model.** Before, layered always honoured named sides (D503); with the code out of core it can only do that when the caller brings it. Architecture does, so no first-party output changes. A third-party caller of `layered` that names sides must call `honourSides(graph, layered(graph))` itself. Nothing warns one that does not: an engine has no diagnostics channel (`mermaid`'s `layoutCall` reports for the engine, and has no way to know the sides were meant), so the rule is written on `LayoutEdge.sides`. Two alternatives were weighed in the review of #1366. (a) A function on `LayoutGraph` (`honourSides`, as first built), which `layered` calls: it breaks DESIGN §6.1, since a graph captured as JSON (the DDLT fixtures) loses it and `structuredClone` throws. (b) Passing the function beside the graph, through `LayoutContext`: `ctx.layout(graph)` takes only the graph, so it means widening `RenderContext.layout` in core's pipeline types and `layoutCall` in `mermaid`'s `draw-context.ts`, outside this spec's files; in bytes it costs about what this does. Keeping the redraw in core instead keeps about 1.7 KB gz in the loaded closure, 632 B more than at `mermaid-v13`, and does not fit the round's budget (D728).

(Knut, 2026-11-26, spec #1335, decision 2.)

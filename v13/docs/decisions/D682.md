# D682: An edge label sits midway along the line that shows

An edge label sits midway along the visible line, between the source's border and the base of the arrowhead (#1148): on the built-in layered engine for every routing (curved, stepped and straight), and under ELK. This applies to every diagram type on those engines. It amends how D154's `headRoom` is used and replaces nothing in D154: the head room stays a constant 7 px that no theme variable changes.

- **The shift.** If every label in a rank of labels has its edge's only arrowhead at the same end, the rank moves `headRoom / 2` toward the other end: 3.5 px in flowchart, class, ER and state. C4 and requirement pass head rooms of their own. ELK moves each such label the same distance along the leg it sits on. A label whose edge has heads at both ends, or none, stays midway between the two nodes. The shift is a constant (D154), so it is exact for the classic arrowheads (`default`, `base`, `dark`, `forest`, `neutral`: gap 0, length 8, a 7 px trim). It is not exact for the redux and neo arrowheads (gap 4, length 10.5, a 13.5 px trim), whose labels sit 3.25 px nearer the head than midway. A shift of 6.75 px would be exact there and 3.25 px off under the classic themes instead; following each theme's trim would make the layout move with the arrowhead variables, which D154 rules out.
- **Stepped routing.** The layered engine came from Pele, which added the shift with `headRoom` set to its arrowhead's full trim and skipped it for `tracks`. In Pele `tracks` was on only for the `step` curves, but in v13 the default curve, `rounded`, routes on tracks, so most diagrams lost the shift. The shift now skips only the grid (text output), whose gaps are whole cells. There, a half-cell shift would round up to an extra row, so text output does not change.
- **Which ends have heads.** `LayoutEdge.heads` (`{ source, target }`) says which ends carry an arrowhead or marker. Without it, the target alone does, as the engine assumed before.

  | Type | Ends with a head or marker | `heads` |
  | --- | --- | --- |
  | flowchart | from the arrow type: `-->` the target, `<-->` both, `---` none | set |
  | class | from the start and end markers | set |
  | ER | both: every relationship has a cardinality marker at each end | set |
  | requirement | the target, or the source for `contains` | set |
  | C4 (`c4-beta`) | `-->` the target, `<-->` both, `---` none | set |
  | state | the target | default |
  | agentflow | the target, or none for `---` | default |
  | use case | from its end markers: the source for the `reversed…` associations, none for the plain line | default |
  | swimlane | its own engine, not the layered engine's label ranks | not affected |

  Two cases are known and left as they are: agentflow's labelled `---` edges and use case's reversed or plain-line associations take the default, so their labels move toward the source when they should not. Both moved the same way before this decision, because those types route with curves.
- **v12** kept the label at the centre of dagre's rank, midway between the nodes, with no allowance for the arrowhead. MIGRATION.md lists the change.

On the size: "Wire it for ER and class, and do 3.5." On the other types: "Wire C4 and requirement". On ELK: "Fix it for Elk. That is where it happens." (Knut, 2026-11-23, spec #1163, ticket #1166.)

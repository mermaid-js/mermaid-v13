# D642: A byte order mark before the front matter is skipped, and the front matter is read

When the first character of the source is U+FEFF, the byte order mark, the front-matter scanner (`scanFrontMatter`, DESIGN §4.1) starts after it. The opening `---` is then found as if the BOM were not there, so the front matter's `title` and `config` apply. Only one BOM, at offset 0, is skipped; a BOM anywhere else is text, as before. Nothing is rewritten: every range and diagnostic is still an offset into the source as written, so the front matter's range starts at offset 1.

Before, the scanner read the BOM as horizontal whitespace, so it became the opening fence's indent, no closing `---` had that indent, and the source was rejected with `UNCLOSED_FRONT_MATTER` (#766). A BOM with no front matter, or before a `%%{init}%%` directive, already rendered.

This differs from v12 on purpose. v12's fence regex fails the same way (its `\1` indent is the BOM), and v12 then trims the BOM away, so it draws the diagram but ignores the front matter. A BOM is how the file was saved, not part of the text, and YAML and Markdown readers skip it. The difference is listed in MIGRATION "Front matter and directives" and in the front-matter fence divergences (`packages/core/src/preprocess/divergences.spec.ts`).

Rejected: matching v12, drawing the diagram and ignoring its front matter.

(Knut, 2026-11-19, spec #988, #766.)

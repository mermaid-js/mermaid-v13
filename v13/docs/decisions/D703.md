# D703: The nightly visual build runs in Argos monitoring mode

The `nightly` Argos build (`visual-nightly.yml`, D631) is uploaded with `ARGOS_MODE: monitoring`. Argos compares a monitoring build with the latest approved monitoring build, not with the build on the previous commit, and never approves one by itself: a difference waits in Argos until a maintainer approves or rejects it. Approving a nightly moves the reference forward. Until then the differences of later nights add up against the same reference.

In CI mode, Argos approved every build on `mermaid-v13` that was not tied to a PR, because it is the project's baseline branch. So each nightly was compared only with the night before and approved at once: 532 changed screenshots on 2026-11-23 and 19 on 2026-11-24 were never looked at. That also meant the nightly could not serve as a fixed reference while a set of fixes lands.

Monitoring builds and CI builds never share baselines, so the PR builds and the push builds that are their baseline (D632) are unchanged. The first monitoring nightly has no approved monitoring build to compare with and shows every screenshot as added; approving it once sets the reference. A nightly that finds a difference posts a failing `argos/nightly` status on its `mermaid-v13` commit until it is reviewed. It is not a required check, so it blocks nothing.

Two alternatives were not chosen. Turning off auto-approval of `mermaid-v13` in the Argos project would also stop the push builds from being approved by themselves, and PRs would have no baseline until each push was approved. A second Argos project for the nightly would do the same as monitoring mode with a second token to keep.

A run of `visual-nightly.yml` started by hand on another branch is also a monitoring build. It is never approved: Argos does not document whether monitoring baselines are kept per branch, so an approved branch run could become the reference for everyone.

Amends D631: the nightly stays its own Argos build, now in monitoring mode.

(Knut, 2026-11-26.)

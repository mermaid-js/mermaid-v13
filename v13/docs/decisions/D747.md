# D747: A packet end bit number that would meet another number is dropped

In a packet row, an end bit number (`packetByte end`, at the right edge of its block) that would come within `bitNumberSpace` (2 px, `layout/metrics.ts`) of another bit number's measured box is not drawn. Start numbers always stay: the number at a block's left edge, and the one centred over a one-bit block. When two end numbers meet, the left one goes.

v12 drew a field's end number flush with its block's right edge and the next field's start number flush with the next block's left edge, `paddingX` apart, with no collision test. With narrow fields and 3-digit numbers they printed on top of each other (`96 97`, `100 101` at `bitWidth: 12`), and with `paddingX: 0` the default `15` and `16` ran together as `1516` (#1268). An end number also meets its own field's start number when the field is narrower than the two numbers; it is dropped then too.

At the default config (`bitWidth: 32`, `paddingX: 5`) an end number is at least `paddingX` (5 px) from the next start number, so no number is dropped and the output is byte for byte what it was.

The reporter proposed a minimum `bitWidth` instead. No config key is added.

Two start numbers that meet still overlap: adjacent one-bit fields whose numbers are wider than `bitWidth`, or a one-bit field's number against the next field's start. The layout invariants (`packages/diagram-packet/src/layout/invariants.ts`) gain the rule that every pair of bit numbers in a row with an end number in it is `bitNumberSpace` apart; pairs of start numbers are exempt.

(Knut, 2026-11-27, spec #1341 T2: accepted as proposed. It does not amend an earlier decision: it changes v12's drawing, which spec #421 had kept.)

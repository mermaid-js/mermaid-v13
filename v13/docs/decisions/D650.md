# D650: Crossings too close for a hop each share one merged hop; amends D537

With `lineHops` on, two or more neighbouring crossings on one straight run that are too close to carry a hop each are drawn as one hop over all of them, instead of none. Before, D537 kept v12's rule: the hops of two close crossings shrink to share the run, and a hop squeezed below 0.6 of the 6px radius is not drawn, so crossings less than about 7px apart drew nothing.

The merged hop runs from the first crossing less its radius to the last crossing plus its radius. With `arc` it is half an ellipse along the run, as tall as a plain hop (6px, or less where the run's ends or a neighbouring hop leave less room); with `gap` it is one break over the same stretch. Crossings at the same point draw one plain hop.

Every hop that draws today draws as before, and nothing else moves: the merged hop takes only the room the plain hops leave. Where that room is less than 0.6 of the radius, the close crossings still draw no hop. The rule is in core's lazily loaded `hopPaths` (`packages/core/src/layout/hops/hops.ts`), so it applies to every type that draws line hops: flowchart, swimlane, class, block, C4, architecture and event modeling. The shared `lineHops` key stays off by default (D537); the swimlane engine (`swimlane.lineHops`) and the ELK plugin (`elk.lineHops`) keep their own defaults, which are on.

Class spreads the relations that leave one side of a box about 5px apart, so #655's class sample draws a hop only with this rule. Rejected: wider end spacing in class, a layout change in every class diagram with several relations on one side.

(Knut, 2026-11-19, spec #995 decision 2, #793.)

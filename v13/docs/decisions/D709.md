# D709: Character references without `;` decode as HTML text decodes them

Core reads a character reference in label text as a browser's HTML parser reads one in text content, where v12 drew its labels:

- A numeric reference needs no `;`: `&#60` and `&#x3c` are `<`. All its digits belong to it; a code point that is NUL, a surrogate or out of range is U+FFFD, as with `;`.
- A name of core's table (D561) that HTML also decodes without `;`, its legacy names, decodes without one, also as the start of a longer word: `&lt` is `<` and `&ltx` is `<x`, the longest legacy name winning. They are `amp`, `lt`, `gt`, `quot`, `nbsp`, `shy`, `copy`, `reg`, `deg`, `plusmn`, `times`, `divide`, `middot`, `sect`, `para`, `pound`, `yen`, `cent`, `laquo` and `raquo`. The full HTML table stays out (D561).
- With its `;`, a name of the table decodes as before. A name that is neither, with or without `;` (`&apos`, `&hearts`, `&bogus`, `&bogus;`), stays as written.

`entityAt`, and `decodeEntities` built on it, apply the rule, so it holds in every label core lays out and in the text the four plain-text types decode (D563). Mermaid's own `#name;` form needs its `;` as before: `#lt` with no `;` stays as written. A `#name;` whose name starts with a legacy name (`#ltx;`) now decodes as v12's browser read the `&ltx;` it made, `<x;`, so it is no longer one of D561's unknown names.

#1313's case: in a state note the `;` ends the statement, so `raw &lt; x` leaves `raw &lt`, which v12 drew `raw <` and v13 drew as written. It now draws `raw <`. This is parity with v12, not a change of language.

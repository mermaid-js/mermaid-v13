## Input: PR mermaid-js/mermaid#8635 (Sidharth, open)
`getConfig()` deep-cloned ~970 keys (~220 µs) per call, several calls per node/edge → **52–65% of render time** (flowchart/class/sequence). Frozen shared snapshot: 1.7–2.8× faster on small/medium; 500-node flowchart only 1.6× (2285→1444 ms) because ELK layout dominates. Lessons: v12 slowness is partly accidental cost, not only DOM measurement; ELK default is the large-graph bottleneck; config should be resolved once and threaded explicitly.

## M2 — ASCII backend (grilling session, 2026-11-02)

Grilled with mermaid-ascii's source in hand (`research/mermaid-ascii.md` §8) and against the M1 code on `feature/1_m1-core-flowchart`. D-numbers D76–D87 are M2's; D88–D99 are reserved for M2.5, D100+ for M3.

| # | Decision |
|---|---|
| D76 | **Who draws.** The flowchart plugin's `ascii` hook draws, reading `FlowModel` + `LayoutModel` as `render` does for SVG. It is a separate, lazily loaded entry (`@mermaid-js/diagram-flowchart/ascii`) named in the manifest, so SVG bundles never load it. The shared **text-grid kit** lives in the `@mermaid-js/core/ascii` subpath: canvas, glyph sets, junction merging and cell text (ported from mermaid-ascii's ~650 lines of drawing code, MIT, R-REL-4), the cell measurer and the repair router. `packages/ascii` is dropped. `LayoutModel` stays pure geometry: no labels, shapes or strokes are added to it (refines D24, D35). R-ASCII-1, R-ASCII-5. |
| D77 | **Unit profile.** Layout depends only on the injected measurer **and an injected `UnitProfile`** (`px` or `cell`), never on the backend (amends D57, R-ARCH-3). Every length constant in a diagram's graph builder (node and group padding, title band, label patch, head room, span inset, wrap width) and in the layout engine (port and track pitches, level margins, snap distances, loop size, the 640 turn threshold) comes from the profile; the builder passes the engine's share through `LayoutGraph.metrics`. The px profile reproduces today's numbers, so SVG output does not change. The cell profile is compact by default (node box label + 4 × lines + 2, node spacing 2, rank spacing 4, edge spacing 1, label patch label + 2, group padding 1, head room 1); `ascii.padding: 'roomy'` gives mermaid-ascii-like spacing. px config values (`nodeSpacing`, `rankSpacing`, `wrappingWidth`) convert at a nominal 8 × 16 px per cell, with minimums. R-ARCH-3, R-ASCII-1. |
| D78 | **Routing.** The ASCII path lays out with `routing: 'stepped'` and an integer **grid quantum** (`LayoutGraph.grid: 1`) so node boxes, ports and tracks land on whole cells, then snaps the routes to cells. A small cell-space A\* with a turn penalty (the **repair router**) re-routes only segments that collide after snapping (through a box, a label, a frame, or two edges in one cell). mermaid-ascii's router is not ported: it is tied to its own placement grid, has one lane between neighbours, lets edges overlap by design and ignores subgraph frames (refines D24). R-ASCII-1. *(Refined by D140.)* |
| D79 | **Charsets.** Two glyph sets: `unicode` (box drawing, the default) and `ascii` (`+ - | > v < ^`), chosen by the config key `ascii.charset`, which diagram text may set (front matter, directives). Glyph tables follow mermaid-ascii (solid `─│`, dotted `┄┆`, thick `━┃` with heavy corners; `- |`, `.` `:`, `=` `I` in ascii; heads `▲▼◄►` / `^v<>`; circle `●`/`o`; cross `✕`/`x`; tees where an edge leaves a box). Unlike mermaid-ascii, **every** junction merges through one lookup, heavy and dashed included. R-ASCII-6. |
| D80 | **API.** `render(id, text, { format: 'ascii' })` (the third argument may be an options object; v12's element argument still works) and `renderSync(text, { format: 'ascii' })` return `TextRenderResult { format: 'ascii', text, columns, rows, diagramType, warnings }`, typed by overloads on `format` so SVG callers keep `RenderResult`. Text uses `\n`, has no trailing spaces and is byte-deterministic. `prepare` loads the `ascii` entry when asked for ASCII. An unsupported type throws `UnsupportedFormatError` from both `prepare` and `renderSync`; syntax errors are the same `MermaidError` as for SVG (no text error image). R-ASCII-4, R-ASCII-5. |
| D81 | **Text in cells.** The **cell measurer** counts grapheme clusters (`Intl.Segmenter`): East Asian Wide/Fullwidth and emoji presentation are 2 cells, combining marks and ZWJ 0; edge labels are measured the same way (mermaid-ascii sizes them in bytes). Each label line is one row. `wrappingWidth` converts to cells (200 px → 25). Markdown bullets stay (`•`/`◦`, `-` in ascii); bold and italic are dropped. R-ASCII-7. |
| D82 | **Drops, shapes, subgraphs.** Output is plain text (ANSI colour is a later Could, `ascii.color`). Features with no text form (style/classDef/linkStyle visuals, curves, images and icons (label kept), bold/italic, click/links/tooltips, accTitle/accDescr) are dropped with **one** warning per feature kind, `ASCII_DROPPED { feature, astIds }`. The front-matter `title` is printed centred on the first line. Shapes map through a table (rect → box; rounded, stadium, circle, ellipse → `╭╮╰╯`; diamond, hexagon → box with `◇` / `< >` at the side midpoints; subroutine → double sides; cylinder → `═` top and bottom; collapsed subgraph → `+` marker); any other shape is a box with one `ASCII_SHAPE` warning listing the shapes. Shape delimiters never leak into labels. Subgraph titles sit on the top border (`┌─ one ───┐`); nested clusters nest; empty subgraphs are drawn as an empty frame (refines D58). R-ASCII-5. |
| D83 | **Goldens.** The 142 mermaid-ascii flowchart fixtures (`ascii/` 92, `extended-chars/` 47, `multibyte/` 3) are ported, each as `input.mmd`, `upstream.txt` (their expected output; header lines such as `paddingX = N` stripped and kept as metadata) and our own reviewed `expected.txt`. Our goldens compare exactly. Against `upstream.txt` only a **structural check** runs (each node label inside a box, each edge label present, each edge connected box to box, same number of arrowheads), because v13's layout places things differently. `ascii-divergences.json` (`{ fixture, kind: 'rejected-input' | 'reinterpreted' | 'structural', reason }`) lists only inputs Mermaid rejects or reads differently and structural failures; unlisted failures and stale entries fail CI, as for `divergences.json`. The 179 sequence and ER goldens wait for M3. R-ASCII-2. |
| D84 | **Width.** `ascii.maxWidth` (columns) becomes the layout's `availableWidth` in cells: tighten first, then turn LR into TB (R-LAYOUT-5). Output is never cropped; if it still doesn't fit, an `ASCII_TOO_WIDE` warning is added. R-ASCII-8. |
| D85 | **CLI.** A zero-dependency `mermaid` bin in the `mermaid` package: `mermaid render [file|-] --format ascii|svg [--charset ascii] [--width N|auto]`, reading stdin when no file is given and writing stdout; `auto` uses the terminal's columns. It uses the table measurer. Diagnostics (R-ERR-2 snippet and caret) go to stderr; warnings only with `--warnings`. Exit 1 on an error, 2 on an unsupported format. No new package; distinct from v12's `mmdc` and the `mermaid-ascii` binary. R-ASCII-4. |
| D86 | **Hooks and DOM.** In ASCII mode `postParse` and `postLayout` run as for SVG; `LaidOut` gains `units` so a hook knows it is looking at cells. `postRender` and `afterMount` do not run, and there is no text post-processing hook in M2. The DOM adapter (`run`, `mount`) stays SVG-only in M2 (refines D52). R-PLUG-2. |
| D87 | **Budget and CI.** `core/ascii` and the flowchart's `ascii` entry are excluded from R-PERF-1 (never loaded for SVG) and have their own CI-checked soft budget of ≤ 15 KB gzip, East Asian width data included. ## M3.5 — plugin platform

M3.5's specs each take their own range: D160–D169 the plugin-platform spec (R-PLUG-4, -5, -7 and R-PERF-8, D106), D170–D179 the optional feature plugins (ELK, math), D180–D189 the `neo` themes (R-THEME-7).

### Plugin platform (grilling session, 2026-11-05)

# #596 T0c: shared line hops in core, lazy chunk (closes #78)

Branch `feature/596_line-hops` (own PR into `mermaid-v13`).

## Exports
- `@mermaid-js/core/layout/hops` (lazy, never re-exported from `./layout`): `hopPaths(paths, style)` (pure: path data of one frame in drawing order → new `d` per line, `undefined` when no hop is drawn on it), `parsePath`, `hopStyle(config, layers, section)` (the precedence), `hopWriter(w, style)` (the edge-path step: passes every call through, notes each `outline('edge', 'path')` line and its frame; `finish` writes the hopped data into the finished markup; nothing with fewer than two lines), `lineHops(analysis)` (default export too: `drawDiagram`'s `edges` for a render, or undefined), `HopStyle`.
- Core: `drawDiagram(plugin, model, ctx, hooks?, edges?)` and `EdgeStep` (wraps the writer, either backing, never the plugin). `@mermaid-js/core/layout/swimlane` also exports `layout` (the engine) and re-exports `lineHops`; ELK's engine carries `lineHops`. `CORE_SECTIONS` in `tools/gen-config` (`swimlane`): core's own engine sections resolve in `CORE_DEFAULTS`.
- `mermaid`: a `LAZY_LAYOUTS` row `lineHops` loads the chunk; `registerLayouts` skips a loader of that name, discovery refuses it, D285's gate makes `layout: lineHops` `LAYOUT_UNKNOWN`. `loadLayout` registers a loaded module's `lineHops` as `Registry.hops` (one property check), so loading `swimlane` or an ELK layout loads hops. A render needs layout `lineHops` only when the shared `lineHops` is on and no engine brought it. The analysis keeps the author's config layers (`sources`).

## Use and specs
- Config: top-level `lineHops` (`false` | `true` | `'arc'` | `'gap'`, default `false`); `swimlane.lineHops` (`'arc'`) and `elk.lineHops` (`true`) override under their engine. **For the maintainer:** `renderSync` without the chunk throws `NotLoadedError` for layout `lineHops` (with `placeholders`: drawn without hops plus `PLACEHOLDER`); `preload({ layouts: ['lineHops'] })` or `prepare()` loads it; preloading `swimlane` or `elk` is enough for those layouts.
- Fixtures: `e2e/diagrams/flowchart/baseline/edges/line-hops-{on,off}.mmd` (a 6-cycle over two ranks, `curve: linear`).
- Specs: core `layout/hops/hops.spec.ts` (rules, writer, frames, drawer, `hopStyle` table incl. invalid values), `stream.spec.ts` (hops keep the stream writer); `mermaid/src/line-hops.spec.ts` (renders, tree backing), `line-hops-lazy.spec.ts` (loading, placeholders, every edge diagram, preload, the name guard), `line-hops-preload.spec.ts` (`preload` swimlane); ELK `hooks.spec.ts` (migrated, precedence) and `preload.spec.ts`; `core-chunks.spec.ts`: hop code in lazy chunks of its own (shared with its entry, since swimlane carries it), none in core; `outline-identity.spec.ts` compares hop fixtures with hops off on both sides and asserts they hop.

## Decisions / gaps
- **Choice:** the shared key accepts `'gap'` too (same values as both engine keys and the one hop function; v12 swimlane accepted it).
- **Choice:** an author's top-level `lineHops: false` turns hops off everywhere; else the key of the section the layout name starts with that the author set, the top-level key the author set, that section's default, `false`. "Set" = a valid value (`false`, `true`, `arc`, `gap`) in `initialize()`, front matter or a directive.
- **Choice:** engines whose own `lineHops` defaults on carry the hop step (`swimlane`, ELK); a third-party engine with such a default must too.
- Known limits: a `postRender` hook sees lines before their hops; a line hand-drawn redraws has no hops; a path whose data equals an edge line's, drawn before it, may be taken for it.
- Not done: B1. The section comes from the layout name asked for, so an `elk.*` name that falls back to `layered` (LAYOUT_UNKNOWN) still reads `elk.lineHops`; knowing the real engine at the draw point costs more than a few bytes.
- ELK: `hops.ts`, `drawLineHops` and `postRender` removed; ELK renders keep the stream writer; hop output byte-identical.
- Not verified by a render: swimlane crossings (placeholder routes never cross until T0b).

# Ticket 22: extension plugins (branch feature/22_m1, worktree .claude/worktrees/t22)
**Core** (`@mermaid-js/core`, `src/pipeline/{extensions,manifest,draw}.ts`):
- `ExtensionPlugin<El = unknown, R = unknown> { id, postParse?(ast, ctx) → ast, postLayout?(laidOut, ctx) → laidOut, postRender?(tree: SvgTree, ctx), afterMount?(el, result, state), claims?: ExtensionClaim[] }`. `ExtensionClaim = 'callbacks'`.
- `LaidOut = {kind:'graph', diagram, layout: LayoutModel} | {kind:'custom', diagram, layout: unknown}`.
- `HookContext` = the frozen `RenderContext` (`Object.freeze({...ctx})`) + `diagram` (plugin id) + `state` (that extension's own `{}` for this render). **Deviation from DESIGN §12.2:** `state` is new and `afterMount` takes it as a third arg, so postParse can hand data (click callbacks) to afterMount. DESIGN §12.2 has a note on this.
- `HookRunner<El, R>`: `register(p)` (same id is replaced in place), `size`, `claims()`, `start(ctx, diagramId) → HookRun`. `HookRun { editsTree, mounts, postParse(ast), postLayout(l), postRender(tree), afterMount(el, result) }`. Hooks run in registration order. A throw becomes `MermaidError('INTERNAL', 'Extension "<id>" failed in <hook>: …')`. postLayout must return the same `kind` and `diagram`.
- `drawDiagram(plugin, model, ctx, hooks?: { run, ast })`: postParse(ast) runs first. The returned AST only goes to the next hook, because the renderer draws the model. Then layout → postLayout → render. When `run.editsTree` is set it renders with `treeWriter()` → postRender → `inertProblem(svg, {securityLevel, linkSchemes, themeStyle: theme.autoDeclarations() !== undefined})`, and a problem gives `MermaidError('INTERNAL', "An extension's postRender output fails the allow-list: …")`. Without hooks it streams as before.
- `readManifest(value) → PluginManifest`: `DiagramManifest {plugin:'diagram', id, formats (default ['svg']), detector?, entry?, export?}` or `ExtensionManifest {plugin:'extension', id, entry?, export?}`. It throws TypeError when an extension has a detector or formats, the kind is unknown, a format is unknown, or the id is bad. Extra keys (flowchart's `types`) are dropped.
**mermaid** (`api.ts`, `registry.ts`; exported from index): type `ExtensionPlugin` = core's `<Element, RenderResult>`, `LazyDiagram`, `ManifestPlugin {manifest, detector?, load()}`, `ExternalDiagram = AnyPlugin | LazyDiagram | ExtensionPlugin | ManifestPlugin`, `readManifest`, `LaidOut`, `HookContext`, `ExtensionClaim`, `PluginManifest`.
- `registerExternalDiagrams([...])` sorts each entry by shape: `manifest` key → manifest; parse+render → plugin; detector+loader → lazy; anything else → extension. An extension activates on registration, and so does a manifest extension: `load()` runs right away, and the entry is `module[manifest.export]`, the module itself, or `default`/`extension`, with the id checked against the manifest. A manifest diagram is lazy and `supportsFormat` reads the manifest's formats without loading it.
- Claims: `hooks.claims()` goes to `DiagramParseContext.claims` in analyse. The cache is cleared on register.
- Each renderSync with at least one extension calls `hooks.start(ctx, plugin.id)`. When `run.mounts` is set, `result.bindFunctions = el => run.afterMount(el, result)`.
**For #16 (DOM adapter):** after inserting the svg, call `result.bindFunctions?.(element)`. That is the only afterMount call site, and nothing in core or mermaid calls it now. Calling it twice runs the hooks twice, so `mount` should call it once.
**For #23 (interactions):** `{ id:'interactions', claims:['callbacks'], postParse(ast, ctx){ ctx.state.callbacks = …from the AST click statements… ; return ast }, afterMount(el, result, state){ bind… } }`. The flowchart model has `callbacks`, but hooks only see the AST and do not see the model. If you need the model, extend `DrawHooks`/postParse rather than reaching around it.
**For #24 (non-graph stub):** a `layoutKind:'custom'` plugin's layout reaches postLayout as `{kind:'custom'}`. See the "hands custom layouts over" test.
**Tests:** `packages/mermaid/src/extensions.spec.ts` covers the fixture extension `recorder(id, log)` (every hook through `createMermaid().render`), the frozen ctx, kind change, custom kind, claims, four hostile postRender edits, a safe link, the fixture diagram `tinypie` by manifest + supportsFormat, the manifest extension, and manifest refusals. `packages/conformance/src/manifests.spec.ts` runs every first-party manifest through readManifest.
**Gaps:** the error code for hook and allow-list failures is INTERNAL (no PLUGIN code, so §11 is unchanged). The postParse result does not reach the renderer. There is no Node or bundler discovery (§12.4); only `registerExternalDiagrams` exists. The registry generator does not use readManifest yet. The `click X callback` flow is not exercised end to end (#23).

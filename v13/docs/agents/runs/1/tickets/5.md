# Ticket 5: preprocess, front matter, YAML (branch feature/5_m1)
All from `@mermaid-js/core/preprocess` (`packages/core/src/preprocess/index.ts`). No module state. Never throws.
**`preprocess(src)` → `{ bodyStart, frontMatter?, directives, diagnostics }`**, all ranges into the original `src`.
- Detect and parse the diagram from `bodyStart`. Front matter is never seen by diagram parsers.
- `frontMatter: { range, yamlRange, data: YamlMap|null, title?, config? }`. `title` = v12 rule (truthy → String).
  `config` = plain, **unmerged** object as written. The legacy top-level `displayMode` is moved to `config.gantt.displayMode` (v12 processFrontmatter).
  A non-mapping `config` → warning `FRONT_MATTER_CONFIG`, ignored. A non-mapping document → warning `FRONT_MATTER_NOT_A_MAPPING`.
- Unclosed fence → error `UNCLOSED_FRONT_MATTER` at EOF, `related` = the opener `---`; `bodyStart = src.length`.
  `----` or `--- x` is not a fence: preprocess says nothing, and detection must reject a stray `---` with v12's message ("Diagrams beginning with --- are not valid…").
- `directives: Directive[]` = `{ kind: 'init'|'wrap'|'other', name, range, argsRange?, args? }`, in source order, found anywhere after `bodyStart` (as v12 does).
  `args` = JSON value (v12 quirk kept: `'` and `"` are interchangeable quotes), a bare word → string, absent if invalid.
  `range` covers `%%{`…`}%%` (multi-line OK). An unclosed directive → error `UNCLOSED_DIRECTIVE` at the opener, and its range ends at the end of its line.
  Invalid JSON → warning `INVALID_DIRECTIVE` at the offending char. Only that directive is dropped.
- **For #7 (config):** in order, merge each `kind === 'init'` directive's `args` (if it is an object), and `wrap` → `{ wrap: true }`.
  v12 also moves an init `config` key to the detected diagram's section (`flowchart-v2` → `flowchart`). That is not done here, because it needs detect.
  Secure-key filtering and sanitizeDirective are not done here either. Prototype keys are already dropped (warnings `YAML_UNSAFE_KEY` / `DIRECTIVE_UNSAFE_KEY`).
- **For #8 (lexers):** directives stay in the text. Skip them as `Kind.Directive` using `PreprocessResult.directives[].range`. Don't rescan for `}%%`: that is quadratic on unclosed input. Comments, CRLF and entities are untouched.
**`parseYaml(src, { start?, end?, indent? })` → `{ value, diagnostics }`**: the YAML subset ported from the reference implementation (js-yaml JSON_SCHEMA semantics). Use it for shape data `@{…}` in place (#8).
- Reading stops at the first error (`YAML_SYNTAX`, `YAML_TOO_DEEP`), and `value` is then null. The message is `Invalid YAML: … .`
- `MAX_YAML_DEPTH` / `MAX_DIRECTIVE_DEPTH` = 64.
- Duplicate keys, tags, aliases and a leading `@` or backtick are errors, as in js-yaml. Anchors `&a` are also errors, which js-yaml accepts (a divergence).
**Tests.**
- `preprocess/*.spec.ts`: v12 frontmatter.spec ported, yaml (expected values = js-yaml literals), directives, linear-time `stress.spec.ts`.
- `divergences.spec.ts`: v12's `frontMatterRegex` as the oracle over v12's regex corpus. The decided list must match exactly.
- `packages/conformance/src/preprocess.spec.ts`: all 2150 e2e `.mmd` files compared with the literal v12 steps (cleanupText, regex, dedent + js-yaml, detectDirective). One listed divergence. js-yaml was added as a conformance devDep.
**Decided divergences.**
- The first fence line closes the block (v12's greedy `\s*` could close at a later one).
- A closing fence at EOF without a newline is accepted.
- Leading blank lines before the opener are accepted (v12 render() rejects them; run() trims them).
- Anchors are rejected.
- Prototype keys are dropped.
- A non-mapping config is ignored.
- One bad directive no longer drops the others.
- An unclosed directive ends at its line.
- Names match exactly (v12 matched `/init\b/` unanchored).
**Gaps.**
- No public-API seam yet: tests use the stage API.
- v12's `="x"`→`='x'` HTML-attribute rewrite (cleanupText) is NOT reproduced. That belongs to label parsing (#8/#10). The corpus showed no front-matter impact.
- Attribution is a header comment only, as for parser-kit's the reference implementation ports. There is no THIRD_PARTY_NOTICES file yet.

# T0b #238 — plugin config fragments and the `layout` manifest kind (D153, D177)

Branch `feature/238_config-fragments-layout-manifest`. Consumers: E2 #240, E3 #241, E4 #242, #218 (T1 #221, T4 #226, T5, T6), M2 #245.

## Manifest (final shape, for #218 to adopt)

```json
"mermaid": { "plugin": "layout", "names": ["elk", "elk.stress"], "entry": "./dist/index.js", "export": "layouts", "config": "./dist/config.js" }
```
`readManifest` returns `LayoutManifest { plugin: 'layout'; id?; names; entry; export?; config? }` (exported from `@mermaid-js/core`). `names`: non-empty, `/^[a-z][a-z0-9.-]*$/i`, de-duplicated. `entry` required. `id` is optional (checked as a plugin id when given), unlike the #218 comment's suggestion; #240's manifest has none. No `detector`/`formats`/`ascii`. Diagram/extension manifests are unchanged (the error now says `"diagram", "extension" or "layout"`).
- The entry's export (`export`, else `default`, else `layouts`/`layout`) is v12's `LayoutLoader[]`, looked up by name (#240's default export fits as is), or one engine for every name.
- `config` names an eager module whose `config` (else default) export is the fragment. Discovery must load it with the manifest, like a detector, and pass it along. #221's `layout` arm needs a `config?: ConfigFragment` field for that, and its loader should resolve the same way `Registry.addLayoutPackage` does (or hand discovery the `ManifestPlugin` arm). Registration rules (D166, explicit wins) stay #221's.
- `registerExternalDiagrams([{ manifest, load, config? }])` registers each name lazily, with one shared `load()`. A manifest with `config` but no `ManifestPlugin.config` is a `TypeError`. A name the entry lacks rejects the render that names it.

## Config fragments (`@mermaid-js/core/config`)

- `ConfigFragment { id; keys: Record<string, KeyTree>; defaults?; aliases?: ConfigAlias[]; themeVariables?: Record<string, string> }`, `ConfigAlias { from; to; when?; value? }`, `checkFragment(value, takenThemeVars)`.
- Plugins carry it as `ExtensionPlugin.config`, `LayoutLoader.config` (E2: put the same object on all nine loaders), or `ManifestPlugin.config`. From registration on, the keys validate, `defaults` merge over core's, aliases apply to every source before the `look` strip and the secure-key check, and `themeVariables` go to `createTheme` as `rules`. Registering a fragment clears the parse and site-config caches. One fragment per `id`; a later one replaces it. Without a plugin nothing changes: no fragment, same resolve.
- `ResolveConfigOptions.fragments` and `ResolvedSite.aliases` are new on core's resolver.

## How a plugin reads its values

Extensions: `ctx.config.<section>` in any hook. Layout engines: `mermaid` now always calls `engine(graph, { config })`, and `LayoutContext.config` is the resolved config, defaults merged in, so `ctx.config.elk.mergeEdges` works (cast; fragment keys are not in `MermaidConfig`). This closes the config half of the GAPS [E3/E4] item. Node metadata (`@{ algorithm }`) is still E3's.

## `gen:config`

`packages/<pkg>/schema/config.fragment.yaml`: an annotated schema (same `x-mermaid` rules) plus `x-mermaid-fragment: { id, aliases?, themeVariables? }`. It writes `<pkg>/src/generated/config-fragment.ts` (`export const configFragment: ConfigFragment`) and a `## \`<key>\` (plugin \`<package name>\`)` section in config-reference.md, with aliases listed. A fragment key that core's schema still has is an error, so E4 removes `elk` from core's schema in the same change. No fragment exists yet, so every generated file is byte-identical. The language-service schema and MIGRATION.md don't include fragments yet.

## Exports
- `@mermaid-js/bundler-plugin/{vite,webpack,rollup,esbuild}`: default (and named `mermaid`) = `mermaid(options?)`, so `plugins: [mermaid()]`. `.`: `unplugin` (the `createUnplugin` instance) and `discoveredModule(projectRoot) → { code, warnings (root-relative strings), root, watchFiles, watchDirs }`; `generate.ts` also has `specifierOf(path)` (POSIX as is, `C:/…` for drive paths, UNC and `\\?\` kept with backslashes). Options: `root?` (overrides the bundler root). Deps: `unplugin` 3.4.0 (exact; 3.5+ are < 2 weeks old), peer `mermaid`.
- `mermaid/discovered` (new export): `export default []` only (scan warnings stay build-time). `index.ts` imports it via `bundled.ts`; when the list has at least one plugin, `createMermaid()` (and the default instance) get `discoverOnFirstUse(api, source)`, awaited before the first render, so extensions are active on it. The source honours `initialize({ discovery: false })` (my reading of D165 for bundles; escalate if wrong). `node.ts` skips Node discovery when the bundled list is non-empty (an SSR bundle built with the plugin has its scan already). `mermaid/slim` is untouched. The `./discovered` export stays public on purpose: the spec names `mermaid/discovered` as the module a third-party bundler integration replaces.
- `mermaid/node-scan` additionally exports `FIRST_PARTY_IDS` (node.ts now uses it too).

## How it works
- Root: Vite `config.root`, webpack `compiler.context`, esbuild `absWorkingDir`, else `process.cwd()` (Rollup); then `findAppRoot` + `scanPlugins(root, { firstPartyIds: FIRST_PARTY_IDS })` (T4 rules, confinement). Rescanned at every `buildStart`.
- `load` hook (filter `/mermaid/(dist/discovered.js|src/discovered.ts)(?query)?$`; only a trailing `?query` is stripped, so `#` in project paths works; then `../package.json` name must be `mermaid`) returns the generated module: `import * as detectorN from "<abs>"` per diagram, entries `{ kind: 'plugin', package, plugin: { manifest: JSON.parse("<json>"), detector: pick(detectorN), load: () => import(entry), loadAscii? } }`, extensions `{ …, plugin: { manifest, load: () => import(entry) } }`. Manifests go through `JSON.parse` so a `__proto__` key stays what readManifest saw. Scan warnings: bundler warnings only (`[mermaid] …`, root shown as `.`), never in the bundle; a detector that is its own entry gets a build warning (lazy split lost). Order/collisions left to the registry (D166).
- Invalidation: `addWatchFile` for the app package.json, the install markers (`node_modules/.package-lock.json`, `.modules.yaml`, `.yarn-state.yml`, `.yarn-integrity`) and each found plugin's package.json; `node_modules` + `@scope` dirs as webpack context dependencies, Rollup/Vite watch files (esbuild takes files only). webpack filesystem cache: the app package.json and existing markers go into `cache.buildDependencies.mermaidPlugins`. A package.json that newly gains a `mermaid` key without an install is not seen until the next install/restart.
- Vite: `config()` adds `optimizeDeps.exclude: ['mermaid']` so dev mode goes through the plugin (not tested: the apps only `vite build`). If another dependency pre-bundles `mermaid` inside itself, dev needs that dependency in `optimizeDeps.exclude` too (README); not solved.
- Rule for plugin authors (README): a detector must not import `mermaid` (it is evaluated while mermaid's index evaluates: a cycle), and should not be the entry.
- Layout manifests (#238): the scan skips them (readManifest rejects). Additive later: one more case in `generate.ts` `entryOf` → `{ kind: 'layout', package, names, loader: () => import(entry).then((m) => m[export ?? 'default']) }`, plus a static import of an eager `config` module when present.

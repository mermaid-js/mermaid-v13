# T1 #221 — registry rules (D166) and the discovered-list seam

Branch `feature/221_registry-rules`. Code: `packages/mermaid/src/{registry.ts,discovery.ts,api.ts,slim.ts}`; spec `registry-rules.spec.ts`.

## Rules (Registry)
- Detection: first-party rows (v12 order) → discovered diagrams sorted by (`package`, id), code-unit order, never `localeCompare` → explicit `registerExternalDiagrams` in call order. Input and batch order never matter. Extension hooks follow the same order (discovered by package then id, then explicit in call order), whenever each arrived: the hook runner is rebuilt after each registration.
- First-party names = every id and v12 type of the full generated table (`mermaid/slim` passes `DETECTORS`, so slim and `mermaid` agree). A discovered diagram with one is skipped. One diagram id, extension id or layout name in two packages: the earlier package wins; the other gets `PLUGIN_SKIPPED`, also when the winner arrives in a later batch and displaces it.
- One package may give several entries; each (package, kind, id or name) counts once, and a repeat is skipped.
- Explicit beats discovered (diagram id, extension id, layout name) without `replace`.
- `registerExternalDiagrams(defs, { replace: true })` takes over a first-party id *or type* (`flowchart`, `pie`, `classDiagram`, `flowchart-v2`): the plugin's detector runs in the first slot of the rows with that id/type, and `detectType` reports the plugin id. This lets a community package fill an unported type. Without `replace`: `TypeError` (`"x" is a first-party diagram id or type; pass { replace: true } …`). `menus.spec.ts` and `e2e/dom/interactions.spec.ts` pass `replace: true`.
- Layouts: discovered names register lazily. `elk`/`elk.*` take over the built-in aliases. `layered`/`dagre` are first-party: only those names are skipped (with a warning); the package keeps its other names. `registerLayoutLoaders` beats discovered. Loads are de-duplicated per name, and an engine whose loader was replaced while loading is dropped.

## The seam (`packages/mermaid/src/discovery.ts`; internal, not exported from `mermaid`)
```ts
type DiscoveredPlugin =
  | { kind: 'plugin'; package: string; plugin: ExternalDiagram } // DiagramPlugin | LazyDiagram | ExtensionPlugin | ManifestPlugin
  | { kind: 'layout'; package: string; names: readonly string[]; loader: LayoutLoader['loader'] };
addDiscovered(api: Mermaid, list: readonly DiscoveredPlugin[]): Promise<readonly Warning[]>;
discoverOnFirstUse(api: Mermaid, source: (config) => DiscoveredPlugin[] | Promise<DiscoveredPlugin[]>): void;
```
- `addDiscovered` never throws. Each skip is `{ code: 'PLUGIN_SKIPPED', message, package }`, returned and queued; the queue goes into the next draw that succeeds (a failing draw keeps it). Extensions load now. Diagrams stay lazy.
- `discoverOnFirstUse` (T4): runs once, awaited at the start of the first `prepare`/`render`/`parse`/`preload` (concurrent first calls share it), with the `initialize()` config (`config.discovery`, D165). Its skips reach the first render. A rejecting source registers nothing and queues `{ code: 'PLUGIN_DISCOVERY_FAILED', message }`. One source per API object.
- `renderSync`, `detectType` and `supportsFormat` neither run nor wait for first-use discovery (documented in TSDoc): `await preload()` (or `prepare`/`render`) first.
- T5: the generated module is `[{ kind: 'plugin', package, plugin: { manifest, detector, load: () => import(entry) } }, …]`; `index.ts` calls `addDiscovered(mermaid, discovered)`. T6: drain `globalThis.mermaidPlugins` into `addDiscovered`; each queue entry needs a `package` (T6 picks the fallback, e.g. the plugin id).
- #238 layout manifests: map `{ plugin: 'layout', names, entry, export? }` to the `layout` arm (`loader: () => import(entry).then((m) => m[export ?? 'default'])`), or make `Registry.resolve` return that arm for a `ManifestPlugin`. `readManifest` is unchanged.

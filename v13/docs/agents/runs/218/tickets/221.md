# T1 #221 — registry rules (D166) and the discovered-list seam

Branch `feature/221_registry-rules`. Code: `packages/mermaid/src/{registry.ts,discovery.ts,api.ts}`; spec `registry-rules.spec.ts`.

## Rules (Registry)
- Detection order: first-party rows (v12 order) → discovered diagrams sorted by `package` (code-unit `<`, not `localeCompare`) → explicit `registerExternalDiagrams` in call order. The order of the discovered input, or of batches, never matters.
- A discovered diagram whose id is a first-party id or v12 type (unported rows such as `pie` included) is skipped. Two discovered packages with one diagram id, extension id or layout name: the earlier package name wins and the other is skipped; a later batch whose package sorts earlier takes the id over (no warning for the evicted one).
- Explicit beats discovered (diagram id, extension id, layout name) without `replace`.
- `registerExternalDiagrams(defs, { replace: true })` takes over a first-party id: the plugin's own detector runs in the first slot of that id's rows (the id's other rows drop), and `detectType` reports the plugin id. Without `replace`, a first-party id throws `TypeError` (`"x" is a first-party diagram; pass { replace: true } …`). `menus.spec.ts` and `e2e/dom/interactions.spec.ts` (the sequence stand-in) now pass `replace: true`.
- Layouts: discovered names register lazily (the entry loads when a diagram names it). `elk`/`elk.*` take over the built-in aliases; `layered` and `dagre` are first-party, so a package claiming them is skipped. `registerLayoutLoaders` wins over discovered.

## The seam (`packages/mermaid/src/discovery.ts`; internal, not exported from `mermaid`)
```ts
type DiscoveredPlugin =
  | { kind: 'plugin'; package: string; plugin: ExternalDiagram } // DiagramPlugin | LazyDiagram | ExtensionPlugin | ManifestPlugin
  | { kind: 'layout'; package: string; names: readonly string[]; loader: LayoutLoader['loader'] };
addDiscovered(api: Mermaid, list: readonly DiscoveredPlugin[]): Promise<readonly Warning[]>;
discoverOnFirstUse(api: Mermaid, source: (config) => DiscoveredPlugin[] | Promise<DiscoveredPlugin[]>): void;
```
- `addDiscovered` never throws. Each unusable package (first-party id, taken id or name, missing or repeated `package`, bad manifest, unknown `kind`, an extension entry that rejects) gives one `{ code: 'PLUGIN_SKIPPED', message, package }`. It is returned, and also prepended once to the next render's `warnings`. Extensions load now and join the hook runner (within one call, in package order). Diagrams stay lazy.
- `discoverOnFirstUse` (T4): the source runs once, awaited at the start of the first `prepare`/`render`/`parse`/`preload` (concurrent first calls share it), with the `initialize()` config (`config.discovery` for D165). A rejecting source registers nothing. One source per API object. `renderSync`/`detectType` do not wait.
- T5: the generated module is `[{ kind: 'plugin', package, plugin: { manifest, detector, load: () => import(entry) } }, …]`, and `index.ts` calls `addDiscovered(mermaid, discovered)`. T6: drain `globalThis.mermaidPlugins` into `addDiscovered`; a queue entry needs a `package` name (T6 picks the fallback, e.g. the plugin id).
- #238 layout manifests: map `{ plugin: 'layout', names, entry, export? }` to the `layout` arm (`loader: () => import(entry).then((m) => m[export ?? 'default'])`), or teach `Registry.resolve` to return that arm for a `ManifestPlugin`. `readManifest` is untouched here.
